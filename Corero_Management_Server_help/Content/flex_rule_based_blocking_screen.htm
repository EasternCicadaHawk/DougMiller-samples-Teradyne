Flex Rule Blocking screen

The CMS provides the Flex Rule utility for defining custom packet-blocking filters. These custom filters enable you to respond quickly to new threats you encounter that are not yet addressed by formal rules in Corero's SmartWall software, or, otherwise, to threats for which you want a very specific or nuanced response that is not provided to your liking by the built-in software. All custom packet filters defined using the Flex Rule utility are associated with a single SmartWall rule (CNS-001037) that indicates that traffic matching one of the filter definitions was recognized.

Clicking Defense Configuration > Flex Rule Blocking in the web UI tool bar displays the Flex Rule Blocking screen for defining these custom filters. The equivalent CLI command is set defense flex-rule-blocking filter filtername.

The Flex Rule Blocking screen provides the following controls:

  • Filter Description – Type a brief explanation for one or more filters.
  • Match Rate Limit – Rule CNS-002010 is triggered when the filtered traffic exceeds this limit. (Note: CNS-002010 will trigger only if rule CNS-001037, the rule associated with matches to the custom filters, is not set to Block, which it is by default.)
  • Add – Click to display the Filter screen to name the filter and define it using tcpdump pcap-filter syntax.
  • Delete – Remove a selected filter from the configuration.
  • Name – The filter's user-defined name. Filters are executed in the alphanumeric order of their names. A filter name cannot be changed after the filter has been created; if you want to change the name of an existing filter, you must delete it and re-create it with the new name.
  • Definition – The pcap-filter expression that defines the custom filter.

These filters block only inbound IP packets which either are not fragmented or are the first fragment of the IP datagram. Non-IP packets are never blocked. Individual filters are combined into a single filter expression by surrounding each expression with parentheses and inserting “or” between them, and rule CNS-001037 is triggered any time one of the filter conditions is met. CNS-001037 is designed to detect and block attacks with extremely high packet rates, and security events are logged only for packets which are also already selected for Sflow sampling. The corresponding blocked and detected counts are accurate, but many fewer events will be shown for CNS-001037 than for comparable packet-based rules.

The filter syntax and behavior is that of the publicly available tcpdump pcap-filter. Refer to http://www.tcpdump.org/manpages/pcap-filter.7.html for additional information. The version supported by the CMS is not necessarily the latest version available from tcpdump.org.

Note these differences between this filter utility and the tcpdump pcap-filter:

  • Hosts must be specified by number rather than by name.
  • The IP broadcast condition is not supported. (There is no means of specifying the subnet mask of an interface.)

Examples

As stated previously, this filter behaves in a way that is very similar to tcpdump pcap-filter, and the keyword syntax and examples provided at http://www.tcpdump.org/manpages/pcap-filter.7.html are very informative if you are unfamiliar with its use.

A few different examples follow here:

  • Filter all packets being sent to port 1024: dst port 1024
  • Filter all UDP packets that are 71 bytes in length and that have a TTL field of 237, 238, or 239 (note the byte offset value [8] specified for the TTL field): udp and len == 71 and (ip[8] >= 237 and ip[8] <= 239)
  • Block traffic from 123.123.123.12 if the source port is 8080 or the source port < 1024,and the destination is 221.211.111.0: src host 123.123.123.12 && (src port 8080 || src port <1024) && dst host 221.211.111.0
  • Block single-tag packets: vlan && dst port 1024
  • Block stacked vlan tagged packets (8100/8100): (vlan && vlan && dst port 1024)
  • Block untagged, single tagged and double tagged traffic (8100/8100 or 9100/8100): (dst port 1024) || (vlan && dst port 1024) || (vlan && dst port 1024)

Note: If you are filtering for VLAN tagged traffic, you must include the vlan keyword in your filter definition explicitly. In addition, when filtering for VLAN tagged traffic, you should be very conscious of how the vlan keyword will affect the decoding offset of the expression; this may not be immediately obvious to you, unless you are already familiar with the nuances of the vlan keyword's behavior. The manpage for the tcpdump pcap-filter command does note this in its description of the vlan keyword, though the statement is embedded in the body of the description without being highlighted in any way:

"Note that the first vlan keyword encountered in expression changes the decoding offsets for the remainder of expression on the assumption that the packet is a VLAN packet. The vlan [vlan_id] expression may be used more than once, to filter on VLAN hierarchies. Each use of that expression increments the filter offsets by 4."

As such, be conscious also of the order in which the vlan keyword appears in the expression, particularly when filtering for some mix of tagged and untagged traffic.
